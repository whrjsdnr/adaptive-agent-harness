# 기능 요구사항

## 1. 목적, 용어, 구현 상태

기존 AI Agent를 실행할 Container Harness를 만들고 실측 결과에 따라 개선하는 플랫폼을 개발한다. 이 문서는 전체 MVP 요구사항이다. 현재 구현 범위는 공통 계약·분석·Harness 패키징 및 Phase 4 Docker Baseline Runner다. 저장소 reference fixture의 실제 Docker 통합 테스트 8개를 WSL2 Linux에서 통과했다. 사용자 Agent·목표 장비 검증, 자동 최적화와 전체 MVP 인수는 미완료다.

| 용어 | 정의 |
| --- | --- |
| Agent | 사용자가 제공한 기존 프로그램과 실행 계약. 플랫폼의 생성 대상이 아님 |
| Harness | Agent 실행을 감싸는 이미지·의존성·환경·입출력 연결·자원 제한·관측 설정 |
| 목표 하드웨어 | 최종 실행을 희망하는 장비의 CPU·메모리·OS·가속기 등 명시적 프로파일 |
| 실행 호스트 | 실제 Docker 실행이 일어나는 장비. 목표 하드웨어와 다를 수 있음 |
| 기준 실행 | 수정하지 않은 Agent와 최초 Harness의 기능·품질·성능 측정 |
| 최적화 후보 | 변경 내용, 근거 실행, 예상 효과, 위험, 검증 조건을 가진 Harness 변형 |
| Incubation | 기준 실행부터 후보 비교·선택 또는 보류까지의 제한된 반복 탐색 |
| Porting Lite | 목표 호환성 평가 및 실행 준비 패키지 생성. 실제 배포나 성능 보증은 제외 |

## 2. 범위와 우선순위

MVP는 단일 실행 호스트, 로컬 Agent 경로, 명시적인 실행 manifest, Docker 백엔드, 로컬 산출물 저장을 우선한다. 여러 입력 유형·특정 Agent 프레임워크를 미리 구현하지 않는다. 첫 실험은 사용자가 제공하는 하나의 기존 Agent와 고정된 벤치마크로 시작한다.

최적화 정책은 측정 기반으로 확장 가능한 계약을 둔다. 초기에는 결정적인 후보 생성기 하나로 시작할 수 있지만, Agent 종류를 입력으로 고정된 설정을 반환해서는 안 된다. 웹 UI, 외부 LLM 호출, 분산 실행은 MVP 필수 조건이 아니다.

| 범위 | 포함 수준 |
| --- | --- |
| Agent·하드웨어 분석, Harness 생성, 실행·벤치마크, 반복 개선 | 후속 MVP에서 구현·검증 |
| 다중 Harness Scheduler | 단일 호스트 최소 큐·동시성·자원 예약·취소 |
| Agent 코드 변경 | 승인·테스트·롤백 계약과 제한된 로컬 패치 경로; 승인 없으면 차단 |
| 보안 하부 Agent | 연동 계약·어댑터·계약 테스트만; 판정 엔진은 별도 시스템 |
| Hardware Porting Lite | 호환성 분석·패키지 생성 |
| 하드웨어 에뮬레이션·VM 실행·실제 드론 배포 | 후속 개발; MVP 제외 |

## 3. 입력·출력 요구사항

### FR-01: 기존 Agent 등록과 보존

- 입력은 로컬 소스 경로, 원본 식별자·해시, 인자 배열 형태의 실행 명령, 작업 디렉터리, 의존성 파일, 입출력 계약, 테스트 명령이다.
- 누락된 정보는 `unknown`과 보완 요청으로 반환한다. 임의의 실행 명령이나 의존성을 확정하지 않는다.
- 초기 분석은 정적 읽기로 제한한다. 패키지 설치·import·실행은 컨테이너 실행 단계에서 수행한다.
- 실행과 변경 실험은 원본을 보존하는 별도 작업 사본에서 수행한다. 분석 실패 시 경로와 오류 코드를 기록한다.

### FR-02: Agent·하드웨어 프로파일 분석

- Agent의 런타임, 진입점, 의존성, 데이터·네트워크·가속기 요구사항과 확인 근거를 기록한다. 유형 분류는 보조 정보다.
- 목표 하드웨어는 CPU 아키텍처, OS·ABI, CPU·RAM 한도, 저장 공간, 가속기·드라이버·런타임, 네트워크·장치 요구를 포함한다.
- 실행 호스트의 실제 정보와 목표 프로파일을 분리한다. 미확인·불일치·확인된 항목을 구분한다.
- 부족한 목표 정보만으로 호환 또는 최적화 성공을 판정하지 않는다.

### FR-03: 기준 Harness 생성

- Agent 코드 변경 없이 Dockerfile, 실행 manifest, 의존성 설치 계획, 입력·출력 연결, 제한·관측 설정을 생성한다.
- Agent가 요구하는 런타임과 플랫폼 제어 코드의 Python 3.12를 구분한다. Agent의 런타임을 일괄 변환하지 않는다.
- 이미지 기반·패키지 버전·컨텍스트 해시를 추적한다. 검증·채택 단계에서는 이미지 digest와 해결한 의존성을 고정한다.
- Agent 원본·호스트 자격 증명·Docker 소켓을 무분별하게 컨텍스트에 포함하거나 컨테이너에 마운트하지 않는다.

### FR-04: 실제 컨테이너 실행과 결과 수집

- 사전 조건을 확인한 뒤 빌드·실행하고, 실행 ID, 이미지 digest, 시작·종료 시각, exit code, stdout·stderr 위치, 오류·취소·timeout·OOM 상태를 남긴다.
- CPU·메모리·PID·실행 시간 제한과 최소 권한을 적용한다. 네트워크는 기본 차단하고 명시적인 요구 범위만 허용한다.
- timeout·취소 시 프로세스와 자원 예약을 정리한다. 실패 기록과 로그는 보존한다.
- Docker가 없으면 환경 차단으로 보고한다. 모의 성공 결과로 대체하지 않는다.

### FR-05: 벤치마크와 기준선

- 동일한 데이터셋·평가 버전·입력·seed·품질 기준을 사용하고, 워밍업과 실측 실행을 구분한다. 기본 제안은 워밍업 1회, 실측 최소 3회다.
- 경과 시간, 처리량, 메모리 최대 사용, 성공률, Agent별 품질 지표를 수집한다. 전력·GPU 사용 등 수집 불가능한 지표는 `null`과 이유로 표시한다.
- 비교 전에 목적 지표·방향·최소 개선 폭·허용 품질 저하·집계법·오차 처리 규칙을 고정한다. 최초 제안은 중앙값, 목표 성능 5% 이상 개선, 품질 저하 0을 사용하되 실험 manifest에서 확정한다.
- 하드웨어·부하·측정 방식이 다르거나 관측 변동이 개선 폭을 설명하면 채택을 보류하고 재측정한다. 목표 장비가 없으면 해당 장비의 실측 결과는 없다.
- 실패한 기준 실행도 후보 생성의 근거가 될 수 있다. 최초 성공 실행을 확보하기 전에는 성능 향상을 주장하지 않는다.

### FR-06: 측정 기반 후보 생성과 탐색

- 후보는 실제 성공·실패 실행 ID와 관측값, 가설, 변경 필드, 검증 계획을 필수로 가진다. 실제 근거가 없으면 생성하지 않는다.
- 의존성·이미지·환경 변수·자원 제한·실행 옵션·관측 설정 등 Harness 조정부터 탐색한다. 가능한 변경 필드를 선언하는 것은 허용하지만 유형별 처방 표는 사용하지 않는다.
- 후보별 변경 범위를 작게 유지하고, 입력·원본 Agent·평가 조건을 동일하게 유지한다. 원인 분리가 불가능한 여러 변경은 채택 근거로 쓰지 않는다.
- trial 수·총 경과 시간·자원 예산·개선 없음 횟수 중 하나가 한계에 이르면 중단한다. 기본 제안은 후보 5개, 총 60분, 연속 개선 없음 3개이며 사용자 manifest에서 확정한다.
- 결과는 채택·기각·판정 보류이며, 실패·품질 저하·비교 불가능·근거 부족을 기록한다. 개선 후보가 없으면 기준 구성을 유지한다.

### FR-07: Agent 코드 변경 통제

- Harness 대안, 실제 실패 근거, 필요한 변경 이유를 포함한 변경 제안서를 작성한다. 자동으로 Agent 코드를 변경하지 않는다.
- 승인 대상은 원본 해시, 정확한 패치 해시, 허용 파일·행동, 승인자·승인 시각·유효 범위, 테스트와 롤백 계획이다. 포괄적인 최적화 요청은 코드 변경 승인으로 간주하지 않는다.
- 승인 후 별도 사본에만 적용한다. 적용 직전 원본·패치 해시를 확인하고, 변경되었으면 승인을 무효화한다.
- 변경 전후 기능·품질 테스트와 롤백 복원·재실행을 수행한다. 실패·취소 시 원본으로 복원하고, 승인·테스트·롤백 증거가 모두 있어야 채택 가능하다.

### FR-08: 최소 Scheduler

- 단일 호스트 FIFO 큐와 기본 동시성 1, 구성 가능한 동시성·CPU·메모리·GPU 슬롯 예약을 제공한다.
- 등록·조회·취소 및 `queued/running/succeeded/failed/cancelled` 상태를 관리한다. 실패·취소 후 예약을 반환한다.
- 벤치마크는 기본적으로 독점 실행하여 동시 작업의 간섭을 막는다. 불가능한 자원 요청은 즉시 거절한다.
- 분산 워커, 선점, 자동 스케일링, 학습 기반 배치는 제외한다. 중단 후 자동 컨테이너 재실행은 하지 않는다.

### FR-09: 보안 하부 Agent 연동 계약

- 이미지·manifest·권한·마운트·네트워크 변경에 대한 요청·응답 계약을 설계한다.
- 외부 응답은 `allow/deny/needs_review/unavailable`과 근거·정책 버전·요청 ID를 포함한다. timeout·스키마 불일치는 `unavailable`이다.
- 보안 서비스가 없으면 보안 검증 완료로 표시하지 않는다. 실행 게이트는 기본 보류하며, 사전 정의된 제한적 로컬 시험 모드는 사용자가 명시적으로 선택할 때만 허용한다. 이 모드는 보안 승인으로 기록하지 않는다.
- 이번 MVP의 자체 구현은 어댑터와 계약 검증까지다. 외부 서비스와의 실제 연동 완료는 별도 증거가 필요하다.

### FR-10: Hardware Porting Lite

- Agent와 Harness의 아키텍처·OS·ABI·의존성 wheel·가속기·메모리·장치 요구를 목표 프로파일과 비교한다.
- 공통 CompatibilityReport는 `FIT/ADAPT_REQUIRED/UNSUPPORTED/UNKNOWN`과 항목별 근거를 사용한다. 향후 Porting Lite도 이 계약을 사용한다. 명백한 불일치는 차단 사유, `unknown`은 추가 확인 항목이다.
- 버전·원본·Harness 해시, 목표 프로파일, 호환성 보고서, Dockerfile·실행 manifest·의존성 정보, 체크섬, 준비·검증·롤백 안내를 패키지로 생성한다.
- 패키지는 실행 준비 자료다. 다른 아키텍처의 이미지 빌드·실행, 에뮬레이션, VM, 장비 배포를 수행하지 않는다. 경고가 있는 패키지에는 실행 적합성 미검증을 표시한다.

### FR-11: 기록과 재현성

- 원본·후보·Harness·목표·실행 호스트·벤치마크·이미지·산출물을 ID와 해시로 연결한다.
- 동일한 기록을 다른 실행에서 덮어쓰지 않는다. 보고서에서 실측, 추정, 모의, 미검증을 구별한다.
- 저장은 로컬 파일 기반으로 시작하고, JSON 버전 계약과 원자적 쓰기를 사용한다. SQLite·서비스 DB는 후속 필요에 따라 검토한다.

## 4. 비기능 요구사항

- 실패·timeout·OOM·취소·보안 거절·호환성 미확인을 서로 다른 원인으로 보고한다.
- 실행 예산·최소 권한·경로 제한·로그 마스킹을 적용한다. 컨테이너가 완전한 보안 격리라는 보장은 하지 않는다.
- 경계 입력은 Pydantic v2로 검증한다. 알 수 없는 필드, 음수 자원, 잘못된 단위·경로·상태 전이를 거부한다.
- 제어부는 Python 3.12로 검증한다. 목표 장비의 의존성과 가속기 지원은 프로파일별로 추가 검증한다.
- 프로젝트 전용 Python 3.12 환경·uv.lock과 Docker 없이 실행하는 계약·분석 테스트를 제공한다. 단위 테스트 통과는 Docker 실행·Agent 기능 동등성·목표 장비 성능 검증을 뜻하지 않는다.

## 5. 아직 확정해야 할 입력

첫 기존 Agent 경로·실행 계약·기능 테스트, 목표 하드웨어 프로파일, 벤치마크 데이터·품질 지표·성능 목표, Docker 실행 호스트, 보안 서비스 계약·접속 방식, 코드 변경 승인자와 승인 저장 방식은 후속 착수 시 확정한다. 이 정보가 없어도 계약·정적 분석·주입된 호스트 관측의 테스트는 가능하지만 실제 최적화와 MVP 인수 검증은 완료할 수 없다.

## 6. 현재 계약·분석 단계

구현된 최상위 계약은 AgentProfile, TargetProfile, HostProfile, OperationalRequirements, HarnessSpecification, CompatibilityReport, BenchmarkResult, AdaptationCandidate, IncubationSession이다. 모두 `schema_version=1.0`, UTC 시각, JSON 왕복 직렬화, 알 수 없는 필드 거절을 제공한다. 식별·참조·해시·명령 등 필수 필드는 누락 시 거절한다. `OperationalRequirements()`의 빈 입력은 모든 요구사항 UNKNOWN을 의미하며 실행 기본값을 추정하지 않는다.

- 각 관측은 `Fact`의 KNOWN/UNKNOWN, 값, 출처, MEASURED/STATIC/DECLARED/SIMULATED/ESTIMATED/UNVERIFIED를 구분한다. UNKNOWN은 null·UNVERIFIED로 표현한다.
- HostProfile의 확인된 값은 실측이어야 한다. TargetProfile은 목표 선언을 별도로 받으며 RESOURCE_SIMULATION의 제한값을 실제 HardwareInfo에 섞지 않는다. 자원 제한을 적용하거나 GPU·OS·아키텍처를 에뮬레이션하지 않는다.
- OS·Architecture·ABI, 물리 자원, 런타임, 배포 지원 정보를 독립 구성한다. GPU 존재와 CUDA 실행, Docker 설치·접근·실행은 별도 항목이다. 추정·시뮬레이션으로 실행 지원을 확정할 수 없다.
- BenchmarkResult는 실제 호스트·목표, Agent/Harness 버전 해시, 실행 ID, 입력·평가 해시, seed·반복·워밍업, 단위·출처·증거별 지표, 기능·품질 검증을 연결한다.
- AdaptationCandidate는 변경 범위·필드·해시·이유, 근거 실행, 추정 효과, 실제 검증을 분리한다. HARNESS 변경은 그 실험의 기준 Agent 버전을 보존한다. AGENT_CODE 변경의 채택 기록에는 승인·전후 테스트·원복 증거 참조가 필요하다.
- IncubationSession은 원본 및 파생 버전을 보존하고, 순서 있는 Baseline → Diagnose → Adapt → Validate의 완료 또는 진행 중 반복을 여러 차례 기록한다. 다른 호스트·목표·Agent의 결과 혼입과 순환 버전 이력을 거절한다.
- ACCEPTED는 실측 실행·지표·기능 PASS·실측 품질 저하 없음·비교 기준 참조를 요구한다. 이는 기록의 유효성 검사이며 최적화 성공을 자동 판정하는 엔진이 아니다.

Compatibility Engine은 알려진 요구사항의 정적 비교만 수행한다. FIT도 실제 실행 보장이 아니며, 의존성 설치·wheel/ABI 호환성은 미검증으로 남긴다. 불일치 또는 미확인 정보를 덮어쓰지 않고 `UNSUPPORTED > UNKNOWN > ADAPT_REQUIRED > FIT` 우선순위로 집계한다. 실제 Agent 입력으로 실행 동등성과 성능을 검증하는 전체 MVP 인수는 후속 단계다.

## 7. Phase 3: Container Harness 생성 범위

- HarnessSpecificationGenerator는 Agent/Target/Host/Compatibility와 ContainerHarnessRequest를 입력받는다. 선택적 OperationalRequirements는 기존 최소 조건을 강화하거나 UNKNOWN을 채우며, 확인된 조건을 약화하지 않는다. Python 프로그램을 Docker로 감싸는 명시적 운영 요구는 허용하지만 VM 요구는 차단한다.
- 명시적인 기반 이미지와 인자 배열을 사용한다. 소스에서 셸 명령을 추출·실행하거나 Agent 유형별 최적화·이미지 선택 정책을 만들지 않는다. 실행 명령이 없으면 미확인 사유와 함께 생성 차단한다.
- 기존 보고서의 UNSUPPORTED를 차단하고 현재 입력으로 호환성을 재평가한다. 이전 UNKNOWN 근거를 숨기지 않는다. 이미지 아키텍처·Python 런타임이 명백히 충돌하면 차단하며, 추정·미검증 정보는 REVIEW_REQUIRED다.
- CPU/RAM은 요청 할당과 Target 시뮬레이션 한도를 항목별 병합하고 물리 용량·선언된 한도를 넘지 않도록 한다. 누락값은 임의의 1 CPU·1 GiB 같은 값으로 확정하지 않는다.
- 비특권 숫자 UID/GID, cap_drop ALL, no-new-privileges, PID 제한을 보안 기본 정책으로 사용한다. read_only는 호환성이 명시적으로 확인된 경우만 설정한다.
- 네트워크 기본 차단은 Compose network_mode none으로 구성한다. 호스트명/IP allowlist는 선언만 기록하고 외부 강제 수단이 준비되기 전 차단을 유지한다. 구성 파일의 정책과 실제 런타임 강제 검증은 별도다.
- 파일은 명시적 소스 allowlist와 해시로 복사하며 원본은 수정하지 않는다. 추가 자산의 해시는 분석 파일 지문과 별도로 추적한다. 호스트 bind는 별도 allowlist에 제한하고 Docker 소켓·장치·symlink·원본을 노출하는 writable bind를 차단한다.
- ContainerHarnessBuilder는 지정된 기존 출력 루트의 새 패키지 디렉터리에만 파일을 쓴다. 기존 출력은 덮어쓰지 않고 실패 시 이번에 작성한 파일만 정리한다. 환경변수 값·자격 증명은 생성하지 않으며 소스·메타데이터의 의심 패턴도 차단한다. 전체 보안 판정 엔진은 구현하지 않는다.
- Linux x86_64/ARM64의 목표 플랫폼 메타데이터와 미실행 BuildxPlan을 제공한다. 실제 기반 이미지 조회·빌드·교차 실행·ARM64 하드웨어 검증·GPU 디바이스 구성·드라이버/CUDA/TensorRT·바이너리 ABI 검증은 하지 않는다.

Phase 3 출력은 Dockerfile·Compose·명세·환경 템플릿·안내문·Manifest·소스 빌드 컨텍스트다. 패키지의 image_built와 execution_verified는 false로 보존하며 Phase 4 실행 증거는 별도 결과에 기록한다. STATIC_READY는 정적 입력의 완전성이다.

## 8. Phase 4: Agent Integration 및 Baseline Runner

승인된 소스·패키지 해시, Analyzer/Host/Target 지문, 명시적 명령·의존성·작업 디렉터리·환경 참조·CPU/RAM 제한을 확인한다. 패키지 사본을 재검증한 뒤 Docker에서만 빌드·실행한다. 외부 보안 서비스 대신 사용자가 선택한 TRUSTED_LOCAL_TRIAL만 지원하며 이를 보안 승인으로 기록하지 않는다.

BaselinePlan은 반복·워밍업·timeout·로그 한도·기대 stdout을 지정한다. 기대 결과가 없으면 기능 UNKNOWN이며 exit 0만으로 PASS가 되지 않는다. 실패·OOM·timeout·정리 오류를 보존하고 기존 BenchmarkResult를 BaselineResult에 포함해 원자적으로 저장한다. 측정 기준과 한계는 [실행 안내](PHASE4_BASELINE.md)를 따른다. 최적화·자동 변경·Scheduler·코드 수정·에뮬레이션·드론 배포는 구현하지 않는다.
